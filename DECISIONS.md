# PersonaBridge Decisions

## Decision 1: Start With Chat, Consent, And Approvals Before Realtime Voice

Status: accepted.

PersonaBridge starts with a Next.js web console and FastAPI session API instead of connecting the model runtime or voice transport first.

Why:

- Chat, memory consent, and tool approval are the product safety boundaries that every later realtime feature must respect.
- A stubbed assistant response keeps local development runnable without model credentials.
- Voice and video add browser permission, token, and transport complexity that should not hide the core session contract.

Rejected alternatives:

- Start with OpenAI Realtime API integration immediately. Rejected because credentials and audio-room behavior would make the first slice harder to validate locally.
- Start with long-term memory storage first. Rejected because memory policy and consent semantics need to be visible in the user workflow before schema design.
- Execute fake tools after approval. Rejected because it encourages demo behavior before the permission model is tied to real tool identities.

## Decision 2: Approval Requests Are First-Class API Resources

Status: accepted.

The scaffold models approval requests separately from chat messages, even though they are currently generated by message content.

Why:

- External actions need an auditable lifecycle: pending, approved, or rejected.
- Future tool execution can require an approved request ID instead of trusting assistant text.
- The UI can show approvals independently from the transcript.

Tradeoff:

- The first implementation uses a lightweight keyword detector and in-memory state. This is acceptable for the scaffold, but it is not a policy engine or durable audit log.
